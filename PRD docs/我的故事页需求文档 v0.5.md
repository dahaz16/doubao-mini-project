# 我的故事页需求文档 v0.5
#1. 工作手记#

此需求为回忆录写作、客户端回忆录展示方面需求。
## 一、基于《服务端流程文档与数据库结构设计 v3.8.md》的改动点
* Topic 表新增字段：topic_writing_state，默认0，取值定义：
  * 0 == pending（已进入写作缓存池，待写作）
  * 1 == writing（写作进行中）
  * 2 == done（已写入回忆录）
* 新增表 “**写作素材缓存池**”：**writing_source_cachepool**，用于存储待写作素材引用池（只存 topic_id，不存正文内容），包含字段：
  * writing_source_id (PK)
  * topic_id (FK)（仅存引用，不存 topic_content）
  * user_id
  * created_time
* 新增表“**写作状态**”：**writing_status**，用于记录缓存池字数与写作任务状态，包含字段：
  * user_id (PK)
  * cachepool_words_count
  * writing_state, 默认0，取值定义：
    * 0 == pending（未进行写作）
    * 1 == writing（正在写作）
  * updated_time
* 新增表“**回忆录章节**”：**memoir_chapter**，用于记录用户的回忆录文章的章节（每个章节对应回忆录数据库中的舞台）内容。包含字段： 
  * chapter_id (PK)
  * link_stage_id (FK)
  * chapter_name
  * chapter_sort_num
  * user_id
  * created_time
* 新增表“**回忆录文章**”：**memoir_article**，用于存储回录文章。包含字段：
  * section_id (PK)
  * topic_id (FK)
  * user_id
  * chapter_id
  * section_name
  * section_content
  * section_sort_num
  * created_time
* 新增配置项： **config.wtr_cache_pool_limit**，用于规定“写作缓存池字数到达多少后允许新一轮写作”。
* 新增配置项： **config.wtr_reference_words_limit**，在配置 Wrt LLM 输入时，用于指定前情提要（reference_article）的最大字数长度。
## 二、服务端流程设计
### 写作缓存池（writing_source_cachepool）
* 定义： 这是一个临时的对话存放区。包含多条待写的 topic。当积累的 topic_content 攒够一定字数后，允许进行新一轮的回忆录写作。
* 更新时机：Topic 表中，新增、更新 topic 时，此 topic 的 writing_state 将变为 0 (pending)，此时触发写作缓存池更新；
* 处理逻辑：
  1. 将新增或更新的 topic_id 插入 writing_source_cachepool 表：
     * 插入前，先检查 writing_source_cachepool 表中是否已有此 topic_id：
       * 若无，则插入；
       * 若已有，则不做任何操作。
     * 赋值：
       * topic_id = 新增或更新的 topic_id
       * user_id = 此用户的 user_id
       * created_time = 当前时间
  2. writing_source_cachepool 表插入完毕后，更新缓存池字数：
     1. 查询 writing_source_cachepool 表中所有 topic_id；
     2. 根据 topic_id 查询 topic 表，读取 topic_title、 Topic.topic_content
     3. 计算字数： writing_source_cachepool_words_count == 所有 topic_title + topic_content 的字数和
     4. 更新 writing_status.cachepool_words_count
     5. writing_status.updated_time = 当前时间
### 写作时机
用户进入“我的故事”页后：若：cachepool_words_count >= config.wtr_cache_pool_limit，则：
* 若 memoir_article 表为空：自动开启写作；
* 若不为空：提示用户更新写作。
### 写作方式
* **配置本轮 writer_llm_input**：
  * 取 prompt：在 prompt_config 表中，取 llm_type == 3 且 is_active == ture 且 prompt_id 最大的记录，wtr_prompt == prompt_content；
  * writing_source： 
    1. pending_topic_ids == writing_source_cachepool 的全部 topic_id；
    2. 拿取 reference_article（即关联 stage 的已有文章，作为前情提要）：
       * 根据 pending_topic_ids 查询所有 topic 表中的 parent_stage_id；
       * 根据 parent_stage_id，查询 memoir_chapter 表中 link_stage_id == parent_stage_id 的 chapter_id，拿到 chapter_name；
       * 根据 chapter_id，查询 memoir_article 表中带有此 chapter_id 的文章全部 section_id，获取 section_name、section_content
       * 拼接：reference_article == {chapter_name} + （chapter 下的所有 section 的） {section_name} + {section_content}。其中：
         * chapter 按照 chapter_sort_num 升序排列；
         * section 按照 section_sort_num 升序排列；
       * 确认字数未超限：若 reference_article 字数 > config.wtr_reference_words_limit，则超出部分需被截断遗弃。
    3. **拿取本轮写作素材**：根据 pending_topic_ids 查询 topic 表中的字段，拿到 topic_title、 topic_content。
    4. 拼接： 按 topic 表的 topic_id 升序拼接，每条记录拼接格式：[{topic_id}]{topic_title}-{topic_content}，例：“ [1]外婆养的小猫-外婆有只奶牛猫，我特别喜欢… [2]外婆做的糯米肉-外婆最拿手的菜是糯米肉…”
  * wrt_llm_input == [ {role: system, content: wtr_prompt}, {role: user, content: writing_source}
* **更新写作状态**：
  * writing_status 表中：writing_state == running
  * topic 表中：所有参与写作的 topic，其 writing_state == writing
* **调用 wtr LLM Response API**：
  * 入参：
    * model_id == 查询 base_models 表获取 api_model_id（条件：model_id == {{config.wtr_llm_model}}）；
    * input == wrt_llm_input；
    * temperature == {{config.wtr_llm_temp}}。
  * 判断 LLM 是否回复成功：
    * 判断回复是否成功：
      * 若 LLM 返回了内容，则判定为回复成功。此时进入下一步；
      * 若 LLM 回复报错，则重试 2 次调用。若仍然回复失败，则：
        * 后端提示“诶？刚才念念写东西时开了个小差（wtrllmRE）”；
        * **执行状态回滚**：
          1. 更新 topic 表：将 current_batch_topic_ids 对应的 topic_writing_state 统一重置为 0 (pending)；
          2. 更新 writing_status 表：将 writing_state 重置为 0 (pending)。
    * 判断 JSON 是否解析成功：
      * 若 JSON 解析失败， 则重试 2 次调用。若仍然回复失败，则： 
        * 后端提示“诶？刚才念念写东西时开了个小差（wtrllmJE）”；
        * **执行状态回滚**：
          1. 更新 topic 表：将 current_batch_topic_ids 对应的 topic_writing_state 统一重置为 0 (pending)；
          2. 更新 writing_status 表：将 writing_state 重置为 0 (pending)。
      * 若 JSON 解析成功，进入下一步。
* **Wtr 输出成功后的处理**：
  * **判断是否需要新建 chapter**：根据 Wtr LLM 的输出中返回的 topic_id，在 topic 表中查找此 topic 的 parent_stage_id，再根据查找到的 parent_stage_id，查看当前 memoir_chapter 表中是否有相同 parent_stage_id 的记录：
    * 若有，则代表已有此 chapter 了，不需要新建，此时不需做处理；
    * 若没有，则创建一条记录（新建 chapter），赋值：
      * chapter_id == 自增数字
      * link_stage_id == parent_stage_id
      * chapter_name == link_stage_id 对应的 stage_title
      * chapter_sort_num == 自增数字
      * user_id == 当前用户ID
      * created_time == 当前时间
  * **写入回忆录文章数据库**： 根据 Wtr LLM 的输出中返回的 topic_id，查找 memoir_article 表中是否有对应此 toipic_id 的记录：
    * 如果有，代表重写了此 topic，将 section_content 更新为 JSON 解析出的 article_content；
    * 如果没有，代表这是一个新的 topic，需创建新记录，并赋值：
      * user_id == 当前用户ID
      * topic_id == JSON 解析出的 toipic_id
      * chapter_id == 先查出 topic 表里此 topic_id 的 parent_stage_id，再在 memoir_chapter 表中查找 link_stage_id == 此 parent_stage_id 的记录，将此字段赋值为这条记录的 id：
      * section_id == 自增 id
      * section_content == JSON 解析出的 article_content
      * section_sort_num == 自增数字
      * created_time == 当前时间
  * **更新 topic 表**：将对应 topic_id 的 topic_writing_state == 2(done)
  * **更新 writing_source_cachepool 表**： 
    1. 执行删除操作，条件为 topic_id IN pending_topic_ids；
    2. 清空 pending_topic_ids。
  * **更新 writing_status 表**，赋值：
    * writing_state == 0 (pending)
    * cachepool_words_count == writing_source_cachepool 中剩余的总字数。
  * **记录 Wtr LLM 调用**： 根据模型返回的 token 消耗，写入 LLM_processed 表，赋值：
    * agent == "Wtr”（需要在 LLM_processed 表中， agent 字段增加此选项）
    * model_id == {{config.wtr_llm_model}}（直接存配置项中的内部 ID）
    * process_duration == 从调用到成功收到回复的时长，由系统计算，单位：毫秒
    * total_tokens == SDK 返回的 total_tokens
    * prompt_tokens == SDK 返回的 prompt_tokens
    * completion_tokens == SDK 返回的 completion_tokens
    * cached_tokens == SDK 返回的 cached_tokens
